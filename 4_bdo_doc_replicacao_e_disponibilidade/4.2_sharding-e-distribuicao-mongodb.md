# 4.2 Sharding e distribuição em MongoDB

A replicação mantém cópias dos dados para aumentar a redundância e a disponibilidade. O sharding distribui documentos entre shards para permitir o crescimento do conjunto de dados e da carga.

Esta aula utiliza exemplos conceituais. Não é necessário configurar servidores ou executar comandos.

---

## Objetivos da aula

Ao final desta aula, o aluno deverá ser capaz de:

- comparar escalabilidade vertical e horizontal;
- reconhecer os componentes de um cluster particionado;
- explicar a função da shard key;
- comparar distribuição por faixa e por hash;
- diferenciar roteamento de consultas e uso de índices;
- relacionar sharding e replicação em uma mesma arquitetura.

---

## 1. Quando um servidor não acompanha o crescimento

Uma central de suporte passou de milhares para milhões de chamados. Os dados históricos ocupam cada vez mais espaço e muitas consultas e atualizações ocorrem ao mesmo tempo.

Antes de distribuir a coleção, é necessário analisar a modelagem, as consultas e os índices, como na aula 3. Uma consulta que lê dados desnecessários pode continuar ineficiente em vários servidores.

| Estratégia de crescimento | Exemplo | Aspecto a considerar |
|---|---|---|
| Vertical | Aumentar CPU, memória ou disco de uma máquina | Limites e custo da máquina |
| Horizontal | Distribuir dados e carga por mais máquinas | Comunicação, coordenação e manutenção |

Sharding é uma estratégia de particionamento associada à escalabilidade horizontal. Distribuir o sistema acrescenta complexidade; não garante redução do tempo de todas as consultas.

## 2. O que é um shard?

Um **shard** armazena uma parte dos dados de uma coleção particionada. Os documentos de uma mesma coleção podem estar em shards diferentes.

```text
Coleção lógica: chamados
          |
          +---- Shard A: parte dos documentos
          |
          +---- Shard B: outra parte dos documentos
```

Para a aplicação, continua existindo uma coleção chamada `chamados`. A aplicação não precisa escolher manualmente o servidor de cada documento.

---

## 3. Componentes de um cluster particionado

| Componente | Responsabilidade |
|---|---|
| Shards | Armazenar os documentos distribuídos; cada shard é um replica set |
| `mongos` | Receber operações, encaminhá-las aos shards e reunir resultados |
| Config server replica set | Manter metadados e configurações sobre a organização do cluster |
| Balancer | Administrar migrações de faixas de dados para equilibrar sua distribuição |

```text
                     Aplicação ou Compass
                              |
                           mongos
                          /      \
                     Shard A    Shard B

       mongos consulta os metadados dos config servers
```

Nesta arquitetura, os config servers são considerados separados dos shards de aplicação. Existem outras configurações possíveis, mas elas não serão necessárias aos exemplos.

O roteador mantém informações sobre a localização dos dados. Os comandos da aplicação passam pelo `mongos`, que decide os destinos relevantes para cada operação.

## 4. Chave de distribuição: shard key

A **shard key** é um campo ou conjunto de campos utilizado no particionamento da coleção.

Considere um chamado com os seguintes dados:

| Campo | Valor ilustrativo |
|---|---|
| Protocolo | CH101 |
| Identificador do cliente (`cliente.id`) | 101 |
| Nome do cliente | Cliente 101 |
| Status | aberto |
| Categoria | rede |
| Data de abertura | 21/10/2026 às 10h |

Uma possibilidade de chave é `cliente.id`. A escolha precisa considerar como os documentos se distribuem e como serão consultados.

| Critério | Pergunta |
|---|---|
| Cardinalidade | Existem muitos valores distintos? |
| Frequência | Alguns valores aparecem em uma parcela muito grande dos documentos? |
| Crescimento | As novas escritas se concentram sempre no extremo de uma sequência? |
| Padrão de acesso | As consultas mais frequentes informam a chave? |

### Comparando candidatas

| Campo | Possível vantagem | Risco ou limitação |
|---|---|---|
| `status` | Aparece nas consultas das filas | Poucos valores e muitos documentos por valor |
| `cliente.id` | Favorece a consulta do histórico por cliente | Um cliente muito grande pode concentrar dados e carga |
| `abertoEm` | Relaciona-se a consultas por período | Valores crescentes podem concentrar novas escritas |
| `protocolo` | Muitos valores distintos | Consultas por cliente ou status podem não informar essa chave |

Alta cardinalidade ajuda, mas não basta. Muitos valores distintos podem coexistir com um valor responsável pela maior parte dos documentos.

## 5. Distribuição por faixa

Na distribuição por faixa, o particionamento considera intervalos dos valores da chave.

Exemplo didático com `cliente.id`:

| Faixa de clientes | Shard responsável |
|---|---|
| Menor que 1000 | A |
| A partir de 1000 | B |

O exemplo simplifica as faixas para facilitar a interpretação. Em um cluster real, elas são descritas por metadados e podem mudar com migrações.

Uma busca pelo cliente `1200` pode ser direcionada a B. Uma busca que inclui clientes dos dois intervalos precisa considerar os dois shards.

### Concentração de escritas

Se uma chave cresce continuamente, como uma sequência de datas de abertura, novas inserções tendem a chegar à faixa dos maiores valores. A existência de vários shards não impede essa concentração por si só.

## 6. Distribuição por hash

Na distribuição por hash, o MongoDB calcula um hash do valor da chave e usa intervalos desses hashes para particionar os dados.

```text
Valor de cliente.id -> cálculo do hash -> faixa -> shard responsável
```

O valor original continua armazenado no documento. O hash não é criptografia nem um mecanismo para ocultar os dados do usuário.

Dois pontos importantes:

- Valores próximos, como `101` e `102`, podem ser atribuídos a faixas de hash diferentes.
- O mesmo valor de chave produz o mesmo hash. Todos os chamados de um mesmo cliente continuam associados à faixa desse valor.

O hash pode melhorar o espalhamento de valores sequenciais, mas não divide a carga de um único cliente muito frequente entre várias faixas.

Consultas por igualdade na chave podem ser direcionadas. Já um intervalo dos valores originais não corresponde necessariamente a um intervalo contínuo dos hashes.

## 7. Exemplo de roteamento de consultas

Considere uma chave hashed em `cliente.id`. Para este exemplo, suponha que os metadados indiquem a distribuição abaixo. Os destinos são hipotéticos, não o resultado de um cálculo real de hash.

| Documento | Cliente | Status | Shard |
|---|---|---|---|
| CH101 | 101 | aberto | A |
| CH102 | 101 | fechado | A |
| CH103 | 102 | aberto | B |
| CH104 | 103 | em_andamento | A |
| CH105 | 104 | fechado | B |
| CH106 | 104 | aberto | B |

### Consulta pelo cliente 101

O filtro informa uma igualdade na shard key. O roteador consegue localizar a faixa e consultar A.

### Consulta por status aberto

O filtro não informa `cliente.id`. Documentos abertos podem estar nos dois shards. O roteador consulta A e B e reúne os resultados.

Esse comportamento é chamado de **scatter-gather**: distribuir a consulta entre shards e combinar as respostas.

### Consulta pelo cliente 104 e status aberto

A igualdade em `cliente.id` permite direcionar a consulta a B. O filtro de status seleciona os documentos relevantes dentro desse shard.

## 8. Shard key e índice não são a mesma coisa

| Recurso | Questão que ajuda a resolver |
|---|---|
| Shard key e metadados de distribuição | Quais shards devem receber a operação? |
| Índice | Como localizar e ordenar os documentos dentro dos shards? |

Considere um índice em `status`. Ele pode reduzir o trabalho da consulta por chamados abertos em A e B, mas não informa ao roteador que todos os chamados abertos estão em apenas um shard.

Para o histórico de um cliente, os mecanismos podem se complementar: a igualdade na chave direciona a operação, enquanto um índice em cliente e data atende ao filtro e à ordenação dos resultados.

---

## 9. Chunks e balanceamento

As faixas de particionamento são chamadas de **chunks**. Elas são organizadas pelos valores da shard key ou de seu hash.

O balancer administra migrações dessas faixas entre shards. Isso não significa reorganizar toda a coleção a cada inserção, nem garantir exatamente metade dos documentos em cada um de dois shards.

Distribuição de dados e distribuição de carga também são diferentes. Dois shards com quantidades semelhantes de documentos podem receber números muito diferentes de consultas.

## 10. Replicação e sharding juntos

Considere dois shards, cada um com três membros que armazenam dados:

```text
                          mongos
                         /      \
                 Shard A          Shard B
                replica set      replica set
                 /   |   \        /   |   \
                A1  A2   A3      B1  B2   B3
```

Dentro de A, os três membros mantêm cópias da parte atribuída a A. Dentro de B, os três membros mantêm cópias da parte atribuída a B.

Se A1 falhar, outro membro elegível de A poderá assumir como primary, desde que existam as condições necessárias para a eleição. B não se transforma automaticamente em uma cópia completa de A.

Se todos os membros de A ficarem indisponíveis, as operações que dependem dos seus dados serão afetadas. Ter outro shard não substitui a redundância do shard perdido.

O desenho mostra apenas os membros dos shards. Os config servers e roteadores são componentes adicionais da arquitetura.
