# 3.2 Atividade prática: otimizando as consultas de um sistema de chamados

Esta atividade deve ser realizada após a explicação sobre índices (3.1). Todos os comandos necessários foram apresentados nos exemplos da 3.1.

O objetivo é montar uma base com volume suficiente, escrever as consultas mais comuns de um sistema, propor índices para elas e **medir** o efeito desses índices, comparando tempo de execução e quantidade de documentos examinados antes e depois.

---

## Cenário

Uma empresa de tecnologia mantém uma central de suporte. Cada solicitação de um cliente gera um **chamado**, que é registrado, distribuído para um atendente e acompanhado até ser fechado.

Com o crescimento da empresa, a coleção de chamados passou a ter centenas de milhares de documentos, e as telas do sistema ficaram lentas. Você foi chamado para analisar as consultas mais usadas e propor índices.

Cada chamado é armazenado como um documento na coleção `chamados`, seguindo a estrutura abaixo:

```javascript
{
  protocolo: "CH250000",
  cliente: {
    id: 1234,
    nome: "Cliente 1234",
    estado: "RS"
  },
  atendente: "atendente7",
  categoria: "rede",
  prioridade: "alta",
  status: "em_andamento",
  tags: ["vpn", "senha"],
  abertoEm: ISODate("2026-09-14T10:32:00Z")
}
```

Observe que os dados principais do cliente estão **embutidos** no chamado, como foi discutido na aula 1.

---

## Parte 1: preparação da base de dados

Crie o banco `aula3_atividade` e escreva um script no `mongosh` que insira os chamados na coleção `chamados`.

A coleção deve ter **no mínimo 300.000 chamados**, inseridos em lotes (veja o exemplo da coleção `eventos` na 3.1).

Regras para os campos:

| Campo | Regra |
|-------|-------|
| `protocolo` | `"CH"` seguido do número do chamado (`CH1`, `CH2`, ...), sem repetição |
| `cliente.id` | número sorteado entre 1 e 20.000 |
| `cliente.nome` | `"Cliente "` seguido do `id` |
| `cliente.estado` | sorteado entre `SP`, `RJ`, `MG`, `PR`, `RS`, `SC`, `BA` |
| `atendente` | `"atendente"` seguido de um número sorteado entre 1 e 40 |
| `categoria` | sorteada entre `rede`, `hardware`, `software`, `acesso`, `financeiro` |
| `prioridade` | sorteada entre `baixa`, `media`, `alta`, `critica` |
| `status` | sorteado entre `aberto`, `em_andamento`, `aguardando_cliente`, `resolvido`, `fechado` |
| `tags` | array com 2 tags sorteadas entre `vpn`, `senha`, `impressora`, `email`, `backup`, `wifi`, `lentidao` |
| `abertoEm` | data sorteada dentro dos últimos 365 dias |

Ao final, comprove o volume e a estrutura com `countDocuments()`, `findOne()` e `getIndexes()`.

## Parte 2: consultas comuns do sistema

A equipe de desenvolvimento levantou as consultas mais executadas pelo sistema. Escreva cada uma delas no `mongosh`.

| Código | Tela do sistema | Necessidade |
|--------|-----------------|-------------|
| C1 | Busca rápida | Localizar um chamado pelo protocolo |
| C2 | Histórico do cliente | Listar os chamados de um cliente, do mais recente para o mais antigo |
| C3 | Fila do atendente | Listar os chamados em andamento de um atendente |
| C4 | Painel de urgências | Listar os 20 chamados abertos de prioridade crítica mais recentes |
| C5 | Relatório semanal | Listar os chamados abertos nos últimos 7 dias |
| C6 | Análise regional | Listar chamados com a tag `vpn` de clientes do RS |
| C7 | Arquivo | Listar todos os chamados fechados |

---

## Parte 3: medição sem índices

Antes de criar qualquer índice, execute cada consulta com `explain("executionStats")` e registre:

- o plano de execução (estágios, como `COLLSCAN`, `IXSCAN`, `FETCH`, `SORT`);
- `nReturned`;
- `totalDocsExamined`;
- o tempo médio de três execuções da consulta.

Meça também o custo de escrita: o tempo necessário para inserir 10.000 novos chamados. Remova esses chamados depois da medição.

---

## Parte 4: proposta e criação dos índices

Para cada consulta de C1 a C6, proponha e crie **um índice**, levando em conta os campos de filtro, de ordenação e de intervalo de cada consulta. Escreva uma justificativa curta para cada índice.

A consulta C7 não deve receber índice nesta etapa.

---

## Parte 5: medição com índices

Repita todas as medições da Parte 3, incluindo o custo de escrita.

Depois, crie um índice que atenda à consulta C7 e meça apenas essa consulta.

## Parte 7: análise crítica

Responda com base nos seus resultados, não apenas na teoria.

1. Em qual consulta o ganho de tempo foi maior? Relacione esse ganho com a diferença entre `totalDocsExamined` e `nReturned` antes do índice.
2. O que aconteceu com C7 após a criação do índice? Explique o resultado.
3. Em C2 e C4, o estágio `SORT` apareceu antes do índice? E depois? O que isso significa?
4. Quanto aumentou o tempo de inserção após a criação dos índices? Como isso influencia a decisão de criar índices?
5. Algum dos índices criados pode garantir uma regra de integridade? Qual?
6. Se o cliente **não** estivesse embutido no chamado, mas apenas referenciado por `clienteId`, como ficaria a consulta C6?

---

## Critérios de avaliação

- Base gerada por script, seguindo as regras e o volume mínimo exigidos.
- Consultas escritas corretamente para cada necessidade do sistema.
- Medições realizadas antes e depois dos índices, para todas as consultas.
- Índices coerentes com o filtro e a ordenação de cada consulta.
- Interpretação correta dos planos de execução e dos números do `explain()`.
- Clareza e fundamentação das respostas da análise crítica.
