# 5.2 Prática: replicação e eleição

Após acompanhar [a montagem na VPS](5.1.1_montagem-replica-set-na-vps.md), use o `rs0` já disponibilizado pelo professor. Execute os blocos no shell do Compass, conferindo a conexão indicada.

Cada aluno usa parte do próprio nome como identificador. Os exemplos usam `ana_silva`; substitua esse texto em todos os comandos. A conta fornecida precisa estar autorizada no banco correspondente. Não execute `rs.initiate()` na VPS compartilhada.

## 1. Preparar as conexões

Cadastre a conexão ao conjunto para operações normais:

```text
mongodb://professor@srv1598762.hstgr.cloud:27017,srv1598762.hstgr.cloud:27018,srv1598762.hstgr.cloud:27019/?replicaSet=rs0&authSource=admin
```

Cadastre três conexões diretas para observação:

```text
mongodb://professor@srv1598762.hstgr.cloud:27017/?directConnection=true&readPreference=secondaryPreferred&authSource=admin
mongodb://professor@srv1598762.hstgr.cloud:27018/?directConnection=true&readPreference=secondaryPreferred&authSource=admin
mongodb://professor@srv1598762.hstgr.cloud:27019/?directConnection=true&readPreference=secondaryPreferred&authSource=admin
```

Em cada conexão, abra **Advanced Connection Options → Authentication** e confira:

| Campo | Valor |
|---|---|
| Method | Username/Password |
| Username | `professor` |
| Password | `zpPXqdsqmtm4rtpTcFbkiX0G` |
| Authentication Database | `admin` |
| Authentication Mechanism | Default |

O ambiente não usa TLS nem VPN: deixe a aba TLS/SSL desativada. O aviso amarelo "TLS/SSL is disabled" é esperado e não impede a conexão. Se aparecer "Authentication failed", apague e cole novamente a senha. A conexão ao conjunto permite descobrir o primary. Uma conexão direta fixa o processo observado; `secondaryPreferred` permite a leitura quando ele é secondary, mas não autoriza escrita nesse secondary.

## 2. Descobrir os papéis

Em cada conexão direta:

```javascript
db.hello()
```

Registre `me`, `primary`, `isWritablePrimary`, `secondary` e `setName`. A porta 27017 não tem garantia de ser primary.

Na sessão com permissão de monitoramento:

```javascript
rs.status().members.map(m => ({
  nome: m.name,
  papel: m.stateStr,
  saude: m.health
}))
```

Se a conta do aluno não tiver essa permissão, o professor apresenta a saída. O aluno pode continuar observando `db.hello()` e seus próprios dados.

## 3. Criar o banco individual e seus dados

Na conexão ao conjunto:

```javascript
use lab5_rs_ana_silva
```

`use` seleciona o banco; sua criação efetiva ocorre na primeira escrita. Execute o comando seguinte apenas na conexão ao conjunto. Ele pode ser repetido, pois atualiza um documento de identificador fixo:

```javascript
db.chamados.updateOne(
  { _id: "ana_silva-CH001" },
  {
    $set: {
      aluno: "ana_silva",
      cliente: { id: 101, nome: "Cliente de teste" },
      assunto: "Falha de acesso à VPN",
      status: "aberto",
      atualizadoEm: new Date()
    }
  },
  { upsert: true, writeConcern: { w: "majority", wtimeout: 5000 } }
)
```

O esperado é uma escrita confirmada. Um timeout ao aguardar a maioria não comprova que a escrita deixou de acontecer. Confira o `_id` antes de decidir repetir uma operação.

## 4. Conferir as cópias

Em cada conexão direta:

```javascript
use lab5_rs_ana_silva
db.chamados.findOne({ _id: "ana_silva-CH001" })
```

Registre o papel do membro e o documento encontrado. Não insira novamente o documento em cada porta: a cópia vem da replicação. Se algum secondary ainda não mostrar o documento, aguarde e consulte novamente. O atraso pode ser pequeno demais para ser percebido manualmente; não é obrigatório observá-lo.

Na conexão ao conjunto, altere o status:

```javascript
db.chamados.updateOne(
  { _id: "ana_silva-CH001" },
  { $set: { status: "em_andamento", atualizadoEm: new Date() } },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)
```

Confira a atualização nos três membros. Uma escrita enviada ao conjunto produziu cópias do mesmo documento nos membros.

## 5. Tentar escrever em um secondary

Escolha uma conexão direta que confirme `secondary: true` em `db.hello()`:

```javascript
db.chamados.updateOne(
  { _id: "ana_silva-CH001" },
  { $set: { status: "teste_no_secondary" } }
)
```

O esperado é recusa de escrita por o servidor não ser primary. Se funcionar, confira novamente o papel: ele pode ter mudado desde a observação anterior.

## 6. Eleição coordenada pelo professor

Todos registram o primary atual. O professor confere a saúde e a sincronização dos secondaries e, na conexão direta ao primary, executa uma única vez:

```javascript
rs.stepDown(60)
```

O primary deixa o papel e fica inelegível pelo período informado. Outro membro elegível deve assumir. A escolha depende do estado do conjunto; não existe uma porta predeterminada para o novo primary.

Durante a transição, escritas podem falhar temporariamente e o Compass pode apresentar erro de seleção de servidor. Acompanhe `db.hello()` nas conexões diretas. Depois de identificar o novo primary, na conexão ao conjunto:

```javascript
use lab5_rs_ana_silva
db.chamados.updateOne(
  { _id: "ana_silva-CH001" },
  { $set: { status: "resolvido", atualizadoEm: new Date() } },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)
db.chamados.findOne({ _id: "ana_silva-CH001" })
```

Compare com a conexão direta ao antigo primary: ela continua apontando para o mesmo processo, agora secondary. Registre como a conexão ao conjunto retomou as operações após a eleição.

## 7. Extensão: falha de processo

O professor pode parar um único serviço ou contêiner usando o gerenciador real da VPS. Os alunos observam a indisponibilidade, aguardam uma eleição se o processo era primary e repetem uma escrita pelo conjunto.

Depois, o professor reinicia o processo e acompanha seu retorno a SECONDARY. Não pare dois membros simultaneamente durante a prática normal. `rs.stepDown()` mantém o processo funcionando; parar o serviço o torna indisponível.
