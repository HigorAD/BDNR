# 4.3 Atividade: replicação e sharding no sistema de chamados da aula 3.2

Esta atividade dá continuidade à [atividade 3.2 — Otimizando as consultas de um sistema de chamados](../3_bdo_doc_indices_e_performance/3.2_atividade-otimizacao-sistema-de-chamados.md).

Na atividade anterior, a coleção `chamados` foi analisada para propor índices e comparar planos de execução. Agora, o mesmo sistema será analisado sob a perspectiva de disponibilidade, replicação e distribuição dos dados.

O trabalho é teórico. Utilize as consultas, os índices e as medições já produzidos na atividade 3.2 como material de consulta. Não é necessário gerar outra base, configurar servidores ou executar novas medições. Se a atividade anterior ainda não foi concluída, use o cenário e as consultas reproduzidos abaixo, registrando hipóteses em vez de resultados experimentais.

---

## Cenário retomado

Uma empresa de tecnologia mantém uma central de suporte com uma coleção de pelo menos **300.000 chamados**.

Cada chamado possui os campos da atividade 3.2:

| Campo | Característica |
|---|---|
| `protocolo` | Identificador do chamado, sem repetição na massa gerada |
| `cliente.id` | Número entre 1 e 20.000 |
| `cliente.nome` | Nome do cliente embutido no documento |
| `cliente.estado` | Um dos sete estados utilizados na atividade |
| `atendente` | Um dos 40 atendentes |
| `categoria` | Uma das cinco categorias |
| `prioridade` | baixa, media, alta ou critica |
| `status` | aberto, em_andamento, aguardando_cliente, resolvido ou fechado |
| `tags` | Array com tags como vpn, senha e wifi |
| `abertoEm` | Data de abertura dentro dos últimos 365 dias |

As consultas continuam sendo:

| Código | Tela do sistema | Necessidade |
|---|---|---|
| C1 | Busca rápida | Localizar um chamado pelo protocolo |
| C2 | Histórico do cliente | Listar os chamados de um cliente, do mais recente para o mais antigo |
| C3 | Fila do atendente | Listar os chamados em andamento de um atendente |
| C4 | Painel de urgências | Listar os 20 chamados abertos de prioridade crítica mais recentes |
| C5 | Relatório semanal | Listar os chamados abertos nos últimos 7 dias |
| C6 | Análise regional | Listar chamados com a tag vpn de clientes do RS |
| C7 | Arquivo | Listar todos os chamados fechados |

Além de consultar os dados com eficiência, a empresa agora precisa tolerar falhas e avaliar o crescimento do banco.

## Parte 2: disponibilidade da central de suporte

Considere que o banco da atividade 3.2 passe a utilizar um replica set com três membros: A, B e C. Todos armazenam dados, têm um voto e podem ser eleitos. A é o primary, e os demais estão sincronizados.

Cada situação abaixo parte do ambiente completo e saudável; os eventos não são cumulativos.

| Situação | Membros que permanecem em comunicação | Existe maioria? | Efeito esperado sobre as escritas após a detecção da falha e eventual eleição |
|---|---|---|---|
| C fica indisponível | A e B | | |
| A fica indisponível | B e C | | |
| B e C ficam indisponíveis | Apenas A | | |
| A fica isolado de B e C pela rede | Grupo A; grupo B e C | | |

Responda:

1. Qual é a maioria necessária? Por que ela é calculada sobre os membros votantes configurados?
2. Na falha de A, por que pode existir uma interrupção temporária antes da retomada das escritas?
3. Se A retornar depois de B assumir como primary, ele precisa recuperar seu papel anterior?
4. Se os três processos estiverem na mesma máquina, o sistema tolera a falha dessa máquina?
5. As três cópias dividem os 300.000 chamados em grupos de 100.000 documentos ou cada membro mantém o conjunto replicado? Explique.

## Parte 3: leitura e confirmação de uma alteração

Um atendente altera o chamado `CH250000` de `em_andamento` para `fechado`. A aplicação recebe confirmação com `w: "majority"`.

Imediatamente depois, uma consulta C2, atendida por um secondary, ainda mostra o status anterior. Uma consulta C7, atendida por outro membro, já inclui o chamado entre os fechados.

1. Os dois resultados são necessariamente incompatíveis? Relacione sua resposta ao atraso de replicação.
2. A confirmação por maioria significa que todos os três membros já aplicaram a alteração?
3. Qual é o papel de read preference na escolha de quem atende C2 e C7?
4. Para a fila de trabalho C3 e para o painel de urgências C4, que consequências uma leitura atrasada pode produzir? Justifique qual atenção essas telas exigem em relação à atualização dos dados.
5. Se a exclusão de um conjunto de chamados for replicada para os três membros, como a empresa poderá recuperar os dados?

## Parte 4: distribuição da mesma coleção

Considere agora uma arquitetura hipotética com três shards e uma chave de distribuição **por faixa em `cliente.id`**.

O mapa abaixo já está definido para a simulação:

| Valores de `cliente.id` | Shard responsável |
|---|---|
| De 1 a 7.000, inclusive | S1 |
| De 7.001 a 14.000, inclusive | S2 |
| De 14.001 a 20.000, inclusive | S3 |

Este mapa é didático. Não é necessário configurar um cluster nem reproduzir essas faixas no MongoDB. Considere que todos os shards possuem documentos e que os metadados do roteador refletem esse mapa.
