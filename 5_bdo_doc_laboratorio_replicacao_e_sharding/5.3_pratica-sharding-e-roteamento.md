## 2. Preparar uma coleção vazia do grupo

No banco exclusivo do grupo, em uma primeira execução:

```javascript
use lab5_sh_g01
db.createCollection("chamados")
db.chamados.createIndex({ "cliente.id": "hashed" })
```

Se a coleção já existir, consulte sua situação. Para repetir o experimento, peça um novo banco ao professor, por exemplo `lab5_sh_g01_t2`, e ajuste o namespace em todos os comandos. Não apague bancos de outros grupos.

Na mesma conexão ao `mongos`, com autorização específica para sharding, o professor ou grupo autorizado executa:

```javascript
sh.enableSharding("lab5_sh_g01")
sh.shardCollection(
  "lab5_sh_g01.chamados",
  { "cliente.id": "hashed" }
)
```

O exemplo usa uma coleção vazia com chave hashed, sem zonas configuradas. O MongoDB pode criar e distribuir intervalos iniciais de hash entre os shards elegíveis; o número inicial de chunks varia com a versão. Isso permite demonstrar a distribuição sem depender de uma grande carga para provocar migrações. Chunks são faixas de particionamento, não novos servidores.

Em MongoDB 6.0 ou superior, `sh.enableSharding()` não é um pré-requisito para `sh.shardCollection()`; aparece aqui como uma etapa explícita e pode exigir permissão adicional. Confira a versão registrada em 5.1.

## 3. Gerar chamados

O bloco gera 10.000 documentos em lotes de 1.000. Execute uma única vez em uma coleção vazia. A quantidade pode ser reduzida pelo professor conforme a capacidade da VPS e o número de grupos.

```javascript
{
  const estados = ["SP", "RS", "PR", "MG"]
  const status = ["aberto", "em_andamento", "fechado"]

  for (let inicio = 1; inicio <= 10000; inicio += 1000) {
    const lote = []
    for (let i = inicio; i < inicio + 1000; i++) {
      const clienteId = ((i - 1) % 1000) + 1
      lote.push({
        _id: "g01-CH" + i,
        protocolo: "g01-CH" + i,
        cliente: {
          id: clienteId,
          nome: "Cliente " + clienteId,
          estado: estados[clienteId % estados.length]
        },
        status: status[i % status.length],
        abertoEm: new Date("2026-10-01T00:00:00Z"),
        grupo: "g01"
      })
    }
    db.chamados.insertMany(lote)
  }
}
```

Confira a visão lógica da coleção pelo roteador:

```javascript
db.chamados.countDocuments({})
db.chamados.countDocuments({ "cliente.id": 101 })
```

Resultados esperados: 10.000 documentos no total e 10 para o cliente 101. A chave é `cliente.id`; valores iguais produzem o mesmo hash, mantendo os documentos desse cliente na mesma faixa.

## 4. Observar a distribuição

Na sessão com permissão de monitoramento:

```javascript
sh.status()
db.chamados.getShardDistribution()
```

Registre os shards com dados e suas quantidades. Os números não precisam ser exatamente iguais. Os formatos das saídas podem variar por versão.

Confira a mesma distribuição pelas conexões diretas às portas 27101 e 27102:

```javascript
use lab5_sh_g01
db.chamados.countDocuments({})
```

Cada shard mostra apenas a sua parte; a soma das duas contagens deve ser igual à contagem feita pelo roteador.

Se os dados estiverem em apenas um shard, confira a existência dos dois shards, o particionamento da coleção e os chunks antes de concluir que houve distribuição. Não interprete apenas a contagem lógica como prova de que dois shards armazenam dados.

## 5. Comparar consultas

Consulta A: igualdade na shard key.

```javascript
db.chamados.find({ "cliente.id": 101 }).explain("executionStats")
```

Consulta B: filtro sem a shard key.

```javascript
db.chamados.find({ status: "aberto" }).explain("executionStats")
```

Localize os nomes dos shards participantes nas saídas. A consulta A deve ser direcionada ao shard responsável pelo hash do cliente 101. A consulta B normalmente envolve ambos os shards do cluster.

Não confunda shards consultados com documentos retornados: uma consulta pode acessar um shard e retornar muitos documentos ou consultar dois shards e retornar poucos. A localização de `shards`, `winningPlan` e `executionStats` varia com a versão e o mecanismo de execução; investigue a saída completa.

Consulta C: igualdade na chave e condição adicional.

```javascript
db.chamados.find({
  "cliente.id": 101,
  status: "aberto"
}).explain("executionStats")
```

A condição de status não retira a informação de roteamento fornecida pela igualdade na chave.

## 6. Relacionar índices e sharding

Crie um índice para o filtro de status e repita a consulta B:

```javascript
db.chamados.createIndex({ status: 1 })
db.chamados.find({ status: "aberto" }).explain("executionStats")
```

Compare os planos, `totalDocsExamined`, `totalKeysExamined` e shards participantes. O índice pode reduzir trabalho dentro dos shards; ele não transforma `status` na shard key. O otimizador pode optar por varredura caso julgue o índice pouco vantajoso.

## 7. Atualização direcionada

Escolha um documento existente:

```javascript
db.chamados.findOne({ "cliente.id": 101 })
```

Na massa gerada, o protocolo `g01-CH101` pertence ao cliente 101:

```javascript
db.chamados.updateOne(
  { "cliente.id": 101, _id: "g01-CH101" },
  { $set: { status: "resolvido", atualizadoEm: new Date() } }
)
db.chamados.findOne({ "cliente.id": 101, _id: "g01-CH101" })
```

Confirme `matchedCount: 1` e a mudança do documento. O filtro informa a chave e o identificador do documento.

## 8. Interpretar os resultados

O roteador fornece uma coleção lógica única. A replicação mantém cópias; o sharding distribui partes da coleção. Neste ambiente, cada shard tem um único membro. Parar um shard perde temporariamente o acesso à sua parcela; o outro shard não contém automaticamente uma cópia dela.

Não derrube shards ou config server durante a atividade normal. Esse teste pode ser planejado pelo professor em uma etapa adicional, com recuperação dos serviços e observação dos erros.
